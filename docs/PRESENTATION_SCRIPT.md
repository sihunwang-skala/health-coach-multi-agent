## 2번. 2:00–5:00 코드 설명 순서

아래 순서대로 보면 됩니다. 먼저 **LangGraph가 전체 흐름을 연결하는 부분**을 보고, 그 안에서 실행되는 **Agentic RAG**, RAG가 호출하는 **MCP**, MCP가 사용하는 **실제 검색 엔진** 순서로 내려갑니다.

### 2:00–2:50 LangGraph·Multi-Agent 전체 흐름

**화면:** `coach/graph.py` 27–70줄 (`[발표 코드 1-1]`부터 순서대로)

**가리킬 코드:**

- 27–44줄: `[발표 코드 1-1]` — `StateGraph`와 Agent node 등록
- 46–59줄: `[발표 코드 1-2]` — guard, Supervisor의 conditional edge, 병렬 실행
- 60–70줄: `[발표 코드 1-3]` — Writer 합류, 안전 검사, 재작성, `MemorySaver`

**말할 내용:**

> 이 파일이 전체 Agent Graph를 조립합니다. 26줄에서 하나의 `StateGraph`를 만들고, 아래에서 Supervisor, Diet Agent, Exercise Agent, Safety Agent, Writer와 기록 관련 node를 등록합니다. 43줄의 첫 경로는 code guard입니다. 응급 표현이면 LLM을 호출하지 않고 바로 119 안내로 가고, 아니면 Supervisor로 이동합니다.
>
> 핵심은 46줄의 conditional edge입니다. Supervisor가 고른 route에 따라 실행할 Agent 목록이 달라집니다. 식단·운동 혼합 질문에서는 48줄처럼 Diet, Exercise, Safety Agent 세 개를 같은 단계에서 병렬로 실행합니다. 세 Agent의 결과는 54줄에서 Writer로 모이고, Writer는 한 번만 실행됩니다. 그다음 `validate`가 답변을 검사해 안전하면 종료하고, 문제가 있으면 한 번 다시 작성하거나 위험 문장을 제거합니다. 마지막의 `MemorySaver`는 기록 삭제 전에 graph를 멈췄다가 사용자 승인 후 이어서 실행하기 위해 사용합니다.

**짧게 강조할 문장:**

> Multi-Agent를 사용한 이유는 Agent 수를 늘리기 위해서가 아니라, 필요한 Agent만 선택하고 혼합 질문의 두 검색을 병렬로 실행하며, 검색이 필요 없는 요청은 별도 경로로 보내기 위해서입니다.

### 2:50–3:40 Diet·Exercise Agent의 Agentic RAG

**화면:** `coach/agents/evidence.py`

**먼저 가리킬 코드:** 130–153줄 (`[발표 코드 2-5]`, `[발표 코드 2-6]`)

**말할 내용:**

> Diet Agent와 Exercise Agent는 이름만 다른 단순 함수가 아니라, 130줄부터 정의한 compiled subgraph를 각각 실행합니다. 내부 순서는 검색어 생성, MCP 검색, 근거 선택, 근거 메모 검증입니다. 148줄의 `evidence_node`가 domain을 받아 같은 subgraph를 식단 또는 운동 논문 묶음에 적용하고, 결과를 domain별 state에 따로 저장합니다. 그래서 두 Agent가 동시에 실행돼도 서로의 결과를 덮어쓰지 않습니다.

**화면을 위로 이동:** 43–127줄 (`[발표 코드 2-1]`부터 `[발표 코드 2-4]`)

**말할 내용:**

> 44줄의 `make_queries`는 원래 질문 외에 더 넓은 질문, 질환·약별 질문, 세부 질문을 만듭니다. 69줄의 `retrieve`는 검색을 직접 구현하지 않고 MCP의 `search_papers` tool을 호출합니다. 82줄의 `pick_notes`는 각 검색어의 상위 문단에서 필요한 근거 두 개를 고르고, 질문에 필요한 내용만 메모합니다. 마지막 `verify_notes`는 메모의 단어를 실제 논문 문단과 비교해 원문에 없는 내용이 섞이면 제거합니다. LLM이 만든 중간 결과도 그대로 믿지 않고 code로 검증하는 부분입니다.

### 3:40–4:15 MCP 논문 검색 tool

**화면:** `mcp_servers/papers_server.py` 18–50줄 (`[발표 코드 3-1]`, `[발표 코드 3-2]`)

Agent는 검색 구현이나 논문 파일 위치를 알 필요 없이 검색어, 개수, domain만 전달합니다. 이 서버는 사용자 이름이나 건강 기록을 받지 않고 검색어만 받습니다. 43줄의 `search_baseline`은 Before 시스템이 사용하는 단일 dense 검색이라서, After와 동일한 서버 안에서도 비교 조건을 분리할 수 있습니다.

**화면:** `coach/retrieval/index.py` 99–160줄 (`[발표 코드 4-1]`부터 `[발표 코드 4-4]`)

## 3번을 따로 말하는 발표안: 4:20–5:00 한계·추가 개선안

이 방식을 선택하면 위 스크립트의 시간만 다음처럼 줄입니다.

- **1번(0:00–1:40):** 세부 task에서 관리자 화면 설명을 빼고, 결과를 1:40까지 말합니다. 응답 시간은 3번에서 설명합니다.
- **2번(1:40–4:20):** Agent Graph 45초, RAG subgraph 45초, MCP 30초, Hybrid Retrieval 30초, 마무리 10초로 설명합니다. `deps.py`는 열지 않습니다.
- **3번(4:20–5:00):** 보고서의 `4-1. Trade-off` 첫 두 행과 `5. 추가 개선` 표를 보여 주며 아래 문장을 말합니다.

**화면:** `PRESENTATION_VIEW.md`의 `Trade-off와 추가 개선`

**말할 내용:**

> 성능을 높인 대신 가장 크게 잃은 것은 응답 시간과 비용입니다. 마지막 100문항 전체 평가에서 건강 질문 1개당 평균 응답 시간은 Standard RAG가 4.1초, 최종 Multi-Agent가 18.2초로 14.1초 더 걸렸고, 질문당 비용은 0.0002달러에서 0.0032달러로 늘었습니다. 다음 단계에서는 서로 독립적인 Query Transformation을 병렬화하고, 자주 쓰는 query와 evidence를 cache하며, Evidence Selection 입력을 줄이겠습니다. 또한 같은 평가를 여러 번 실행해 평균과 신뢰구간을 제시하고, code rule에 문맥을 판단하는 작은 classification model을 결합해 안전 검사의 오탐을 줄이겠습니다.

**마지막 한 문장:**

> 즉, 현재는 품질과 안전성을 입증했고, 다음 목표는 그 성능을 유지하면서 더 빠르고 안정적인 서비스로 만드는 것입니다. 감사합니다.

### 느낀점(마지막 10초)

**화면:** 같은 `PRESENTATION_VIEW.md` 화면을 유지합니다. 영상은 틀지 않습니다.

**말할 내용:**

> 직접 구현해 보면서 Multi-Agent는 Agent를 많이 붙이는 것이 아니라, 각 요청에 필요한 역할만 나누고 안전하게 연결하는 설계라는 점을 배웠습니다. 앞으로는 이 구조를 유지하면서 응답 시간과 비용을 줄여 보겠습니다. 감사합니다.

이 3개 구간 발표안에서는 1번 끝에 Trade-off를 미리 말하지 않습니다. `결과의 의미와 구현 방법을 코드에서 보여드리겠습니다`라고만 연결한 뒤, Trade-off와 개선안은 3번에서 한 번만 설명합니다.

## 시간이 밀릴 때 줄일 부분

- 2분 설명에서 사용자 화면 세부 기능은 생략합니다.
- `evidence.py`에서는 `make_queries`, `retrieve`, `verify_notes` 세 함수만 말합니다.
- `user_server.py`와 `deps.py`는 열지 않고 한 문장으로만 설명합니다.
- 수치를 모두 읽지 말고 답변 점수, 안전 문제, 건강 질문 외 처리율, 응답 시간 네 가지만 말합니다.

## 발표 중 피해야 할 설명

- 코드 한 줄씩 읽지 않습니다. 각 코드 묶음이 맡은 역할과 설계 이유를 말합니다.
- “Agent가 많아서 Multi-Agent입니다”라고 설명하지 않습니다. routing, 병렬 실행, 상태 분리, 불필요한 검색 생략을 근거로 설명합니다.
- RAG 성능과 최종 답변 점수를 같은 지표처럼 말하지 않습니다. 근거 회수율은 검색 성능이고, 답변 점수는 최종 답변이 필수 내용을 포함했는지 평가한 값입니다.
- 응답 시간이 늘어난 사실을 숨기지 않습니다. 성능 향상과 함께 Trade-off로 먼저 밝힙니다.
