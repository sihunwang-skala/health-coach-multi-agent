## 1. 문제 — 왜 이 서비스가 필요한가

### 1-1. 대상
**제2형 당뇨병이 있는 고령자(65세 이상)와 그 보호자.** 특히 다음 중 하나 이상에 해당하는 사람입니다.
- 저혈당을 일으킬 수 있는 약(인슐린, 설포닐우레아 계열 먹는 약)을 쓰는 사람
- 신장병, 망막병증, 신경병증, 고혈압 같은 합병증이 있는 사람
- 낙상 위험이 있거나 식사가 불규칙한 사람

### 1-3. 해결하려는 문제
국내 65세 이상 성인의 당뇨병 유병률은 29.3%이지만, 당뇨 자기관리 교육 참여율은 병원·의원 23.2%, 보건소 5.3%에 그칩니다. 따라서 일상에서 반복되는 식단·운동 질문에 언제든 답하면서도, 개인의 질환과 약을 고려해 위험한 조언을 막는 서비스가 필요합니다.

Standard RAG는 질문과 관련된 논문 근거를 찾아 답변하는 데 그칩니다. 이 프로젝트는 여기서 더 나아가 **자체 DB에 저장된 사용자의 질환·복용 약·생활 습관·건강 기록을 질문과 결합**해 개인별 답변을 제공합니다. 또한 다음과 같이 논문 검색만으로 처리할 수 없는 상황도 하나의 서비스 안에서 처리합니다.

1. **개인 맞춤 답변**: 같은 운동 질문이라도 인슐린 사용자는 저혈당, 망막병증 환자는 고강도 운동 위험을 반영합니다.
2. **Safety Guard와 외부 안내**: 위험한 조언을 차단하고, 약 변경은 의료진에게, 응급 증상은 119로 안내합니다. 상담이 필요한 요청은 관리자에게 전달합니다.
3. **서비스 기능과 개인정보 보호**: 건강 기록을 저장·조회하고, 삭제는 사용자 승인을 받은 뒤 실행합니다. 다른 사람의 정보 요청은 거절합니다.

### 1-4. 인사이트와 가능성
- 고령 당뇨 환자에게 필요한 것은 교과서 답이 아니라 **"내 약과 내 병을 고려한 안전한 답"**입니다. 실제로 일반 질문은 표준 RAG도 84.5%를 맞혔지만, 본인 질문은 68.2%에 그쳤습니다(3절).
- 위험 판단을 LLM에만 맡기지 않고 **코드 규칙(응급 감지, 안전 규칙표, 위험 조언 검사)**으로 감싸면 안전 문제를 0%로 만들 수 있었습니다.
- 가능성: 보건소·병원의 만성질환 관리 프로그램, 보호자용 모니터링(관리자 화면), 다른 만성질환(고혈압, 신장병)으로 같은 구조 확장.

## 2. 개선·추가 포인트

### 2-1. 진행 계획표 (과제 양식)
| 순번 | 영역 | 개선 내용 (전 → 후) | 구현 방법과 효과 |
|---|---|---|---|
| 1 | RAG | 질문과 비슷한 문단만 찾는 Standard RAG<br>→ **Health Agentic RAG** | 당뇨 식단 RAG 사전 실험(PoC)에서 130여 차례 비교해 검색 방식을 결정했습니다.<br>· 원래 질문 외에 더 넓은 질문, 질환·약별 질문, 세부 질문을 만듭니다.<br>· 의미가 비슷한 문장을 찾는 dense 검색과 단어가 정확히 일치하는 BM25를 함께 사용합니다.<br>· 찾은 문단 중 필요한 근거만 고르고, 요약한 메모가 원문과 일치하는지 다시 검사합니다.<br>→ 필수 답변을 뒷받침하는 논문 문장을 찾아온 비율이 31.6%에서 58.2%로 높아졌습니다. |
| 2 | Multi-Agent | 하나의 처리 흐름<br>→ **Supervisor + 전문 Agent** | · Supervisor가 메시지마다 처리 경로를 고르고, 본인 질문과 일반 질문을 구분<br>· 식단 Agent·운동 Agent(각각 compiled subgraph)를 동시에 실행<br>· Safety Agent(안전 규칙), Records Agent(기록)<br>→ 건강 질문 외 메시지 처리 35.0% → 97.5% |
| 3 | 안전 | LLM 답변을 그대로 전달<br>→ **응급 감지 · 안전 규칙표 · 위험 조언 검사** | · 응급 표현은 LLM보다 먼저 코드로 감지해 119 안내<br>· 질환·약별 안전 규칙 14개 (운동 R1–R8, 식단 D1–D6)<br>· 답변을 코드 규칙 9개(S1–S9)로 검사해 1회 재작성, 그래도 위험하면 문장 삭제<br>→ 안전 문제가 있는 답변 8.3% → 0% |
| 4 | HITL<br>(사람이 판단하는 지점) | AI가 끝까지 처리<br>→ **사람에게 넘기는 지점 두 곳** | ① 사용자: 기록 삭제 직전 LangGraph `interrupt()`로 멈추고, 사용자가 승인하면 재개해 삭제<br>② 운영자(의료진·상담 인력): 응급·상담 요청·약 변경·다른 사람 정보 요청이 관리자 화면에 "open" 알림으로 뜨고, 운영자가 확인 후 "처리 완료"로 표시 |
| 5 | MCP | 검색·데이터 기능이 Agent 코드 안에 섞임<br>→ **MCP 서버 2개로 분리**<br>(논문 검색 / 사용자 프로필·기록) | · 논문 검색 서버: 검색어만 받음. 누구의 질문인지 모름<br>· 사용자 서버: 프로필을 줄 때 **이름과 ID를 빼고(마스킹)** 나이·질환·약·생활습관만 돌려줌<br>→ 장점 1: 각 서버가 꼭 필요한 정보만 다루므로, 한 곳이 잘못되거나 외부로 나가도 드러나는 개인정보가 줄어듦<br>→ 장점 2: 표준 tool interface라 다른 Agent·MCP 클라이언트에서 그대로 재사용할 수 있고, 테스트에서는 mock MCP 서버로 교체 가능 |
| 6 | 개인정보 | 대화 전체가 외부 서비스로 나감<br>→ **이름 제거 · LangSmith 내용 숨김 · 자체 모니터링 로그** | · 전제: 실서비스는 OpenAI와 **기업용(Enterprise) 계약 — 학습 미사용, 데이터 비보관(zero data retention)** 을 맺은 상태로 가정 (현재는 가상 사용자로 개발·평가만)<br>· OpenAI로는 이름을 뺀 건강 정보와 질문만 보냄<br>· LangSmith에는 단계 구조·시간·token만 보내고 입력·출력은 숨김<br>· 대화 내용은 우리 서버의 자체 로그에만 저장, 90일 뒤 삭제 |
| 7 | 서비스 | 채팅 창 하나<br>→ **사용자 화면 + 관리자 화면** | · 사용자: 채팅 중심, 내 정보·기록은 펼칠 때만, 책임 범위 안내 문구<br>· 관리자: 전체 사용자, 응급·상담 요청 알림, 사용자별 대화·기록·혈당 그래프, 날짜별 사용량·비용 그래프 |

**구조를 말로 설명하면 (메시지 하나가 처리되는 순서)**
1. 사용자가 채팅 화면에서 질문하면 **FastAPI**가 받아서 LangGraph 그래프를 실행하고, 진행 단계를 SSE로 화면에 실시간으로 보냅니다.
2. 먼저 **응급 감지(코드)**가 "가슴 통증, 식은땀·떨림" 같은 표현을 찾습니다. 있으면 LLM을 부르지 않고 바로 119를 안내합니다.
3. 응급이 아니면 **Supervisor(LLM)**가 이 메시지를 어디로 보낼지 정합니다. 식단·운동 질문인지, 기록·상담·약 변경 같은 서비스 요청인지 나누고, 본인 질문인지 일반 질문인지도 구분합니다.
4. 식단·운동 질문이면 **Diet Agent·Exercise Agent**가 MCP로 논문을 검색해 근거 메모를 만들고(필요하면 둘이 동시에), **Safety Agent**는 이 사용자의 질환·약에 맞는 안전 규칙을 고릅니다.
5. **Writer(LLM)**가 근거 메모와 안전 규칙으로 답변을 쓰고, **위험 조언 검사(코드)**가 통과시킨 답만 내보냅니다. 위험하면 1번 다시 쓰고, 그래도 위험하면 그 문장을 지웁니다.
6. 기록 저장·조회는 **Records Agent**가 MCP 사용자 서버로 처리하고, 기록 삭제는 **사용자 승인** 뒤에만 실행합니다. 약 변경·상담 연결·다른 사람 정보·개인정보 질문에는 정해진 안전한 답을 줍니다.
7. 모든 메시지는 **자체 모니터링 로그**에 남고, 응급·상담 요청은 **관리자 화면**에 알림으로 떠서 운영자가 확인합니다.

### 식단·운동 Agent의 논문 근거 검색 과정

건강 질문은 다음 네 단계로 처리합니다.

1. **질문 나누기**: 한 질문을 여러 검색어로 바꿉니다.
2. **논문 찾기**: 의미와 단어가 맞는 논문을 함께 검색하고, 사용자와 맞지 않는 논문은 제외합니다.
3. **근거 확인**: 답변에 필요한 문단만 고르고, 실제 원문에 있는 내용인지 확인합니다.
4. **답변 작성**: 확인된 근거와 Safety 규칙만 사용합니다. 근거가 없으면 추측하지 않고 답변을 보류합니다.

### 2-3. 핵심 강점 4가지
1. **Agentic RAG 설계**: 질문을 여러 검색어로 나누고, 논문을 찾은 뒤 근거를 확인하고 답변하도록 구성했습니다. 각 단계는 실험으로 확인했으며, 표준 RAG보다 정답 근거 회수율이 31.6% → 58.2%로 높아졌습니다(3-3).
2. **MCP 기반 Multi-Agent 구조의 효과 검증**: 같은 Health Agentic RAG를 사용하는 Single-Agent와 통제 비교했습니다. Supervisor의 경로 선택과 본인·일반 질문 구분으로 일반 질문 점수 85.7% → 95.2%, 건강 질문 외 메시지 처리율 35.0% → 97.5%를 달성했고, 불필요한 검색을 생략해 100개 기준 평균 응답 시간 14.0초 → 11.8초, 총비용 $0.218 → $0.198로 줄었습니다(3-4).
3. **안전성과 개인정보 보호 설계**: 응급 상황은 코드 규칙과 LLM의 이중 감지로 5/5를 119로 안내했고, 위험 조언은 규칙 기반 출력 검증으로 0%를 달성했습니다. 개인정보는 MCP 서버 분리와 마스킹, LangSmith 입력·출력 비공개, 자체 모니터링 로그로 외부 노출 범위를 최소화했습니다(2-7).
4. **과제 요구 기술의 실제 구현**: Multi-Agent(LangGraph), MCP, RAG, 의존성 주입, LangSmith, 모듈화, 단위 테스트 20개, FastAPI + SSE를 코드로 구현했습니다. 사용자 화면과 관리자 화면을 만들고, 기록 삭제 전 사용자 승인과 위험 상황 확인을 위한 운영자 알림도 추가했습니다.

| 자체 모니터링 로그 | 대화 내용이 우리 서버 밖으로 나가지 않음, 응급 알림에 바로 사용 | 분석 화면을 직접 만들어야 함 | **운영용으로 구현** (`coach/tracelog.py`, 관리자 화면) |
| LangSmith Enterprise / 자체 서버에 설치한 Langfuse | 개인정보·의료정보 보호 계약(DPA·BAA)을 맺거나 자체 서버에서 운영해, 질문과 답변 내용까지 통제된 환경에서 추적 | 계약 비용 또는 자체 서버 운영 부담 | 실서비스 전환 시 검토 |

외부 LLM(OpenAI)은 개발·평가용이고 사용자는 모두 가상 인물입니다. 실서비스는 학습 미사용·데이터 비보관(zero data retention) 계약을 전제로 하고, 그래프 코드는 그대로 둔 채 LLM만 바꿔 끼울 수 있게(의존성 주입) 했습니다. 자세한 데이터 흐름은 [SAFETY_PRIVACY.md](SAFETY_PRIVACY.md).

## 3. Before / After 수치 — Baseline 대비 성능 평가

### 3-1. 실험 설계 (controlled comparison)
여기서 **Ablation**은 특정 구성 요소의 효과만 확인하기 위해 다른 조건을 같게 두고 그 요소만 넣거나 뺀 비교 시스템을 뜻합니다. **Proposed**는 실제 서비스에 사용한 최종 Multi-Agent입니다.

| 시스템 | 역할 | 구성 | 비교 목적 |
|---|---|---|---|
| **Standard Paper-Search RAG** | **Baseline (Before)** | Naive RAG: 단일 query → dense top-5 → LLM 1회 생성<br>근거 밖 내용은 모델의 일반 지식으로 보완 허용 | 일반적인 논문 검색 RAG의 기준 성능 |
| **Health Agentic RAG** | Ablation ① (RAG만) | Query Transformation → Hybrid Retrieval → Evidence Selection → Faithfulness Check → Grounded Generation<br>안전 계층 없음 | Baseline 대비 **검색 파이프라인의 효과**만 분리 |
| **Single-Agent + Health Agentic RAG** | Ablation ② (단일 Agent) | 위 + 안전 계층(응급 감지, Safety Agent 규칙, 위험 조언 검사)<br>Agent 1개가 모든 메시지 처리, 라우팅 없음 | Multi-Agent의 비교 대상(같은 RAG·같은 안전 계층) |
| **Multi-Agent + Health Agentic RAG** | **Proposed (After)** | 위 + Supervisor 라우팅·본인/일반 질문 구분, Diet·Exercise Agent 분리(병렬), Records Agent, 정해진 안전 응답 | 최종 서비스 |

- **비교 ① RAG 효과**: Baseline ↔ Ablation ① (둘 다 안전 계층 없음)
- **비교 ② Multi-Agent 효과**: Ablation ② ↔ Proposed (RAG와 안전 계층은 동일, 차이는 Agent 구조뿐)
- **통제 조건**: 4가지 시스템 모두 같은 질문 100개, 같은 논문 코퍼스 86편, 같은 사용자 프로필(마스킹), 같은 LLM(GPT-6 Luna)으로 질문당 1회 실행
- **재현성**: 모든 표의 계산 근거와 지표 정의는 [전체 평가 결과](../eval/results/metrics_tables.md)에 있고, 수치는 `eval/make_tables.py`가 결과 파일에서 직접 계산합니다.

### 3-3. 비교 ① RAG 효과 — Baseline ↔ Health Agentic RAG
- **검색 성능이 1.8배**: 꼭 필요한 근거를 찾아 온 비율 31.6% → 58.2%. 본인 질문에서는 19.6% → 50.0%(2.5배).
- **답변 점수는 비슷**(75.3% ↔ 73.2%): 답변 규칙이 다르기 때문입니다. 표준 RAG는 근거에 없으면 모델의 일반 지식으로 채우고, GPT-6 Luna는 아는 것이 많아 점수를 받습니다. Health Agentic RAG는 환각을 막으려고 근거에 없는 내용은 말하지 않아 "자료에 없다"고 답한 항목이 0점이 됩니다. 이것이 이번 설계의 trade-off입니다(4절).
- 답변 점수로 본 RAG 효과는 당뇨 PoC에서 확인했습니다: 같은 식단 본인 질문 50개에서 표준 논문 RAG 0.590 → 최종 Agentic RAG 0.843, 근거 비율 28.9% → 65.1%(PoC 당시 모델 gpt-4o-mini).

**단일 Agent일 때 무엇이 문제였나**
- 인사·잡담에도 논문 검색을 돌려 메시지당 약 11초를 쓰고 "연구 자료에 없으니 의사에게 물어보세요"라고 답했습니다(잡담 10개 중 8개 실패).
- 기록 저장·조회·삭제, 상담 연결, 개인정보 안내를 할 경로가 없습니다.
- 코드 검사에 걸리지 않는 응급 표현("가슴이 조이고 숨이 차요", "어지럽고 시야가 흐려요")에 "의사에게 연락하세요"라고만 답했습니다.
- 일반 질문에도 개인 질환으로 검색어를 좁혀, 질문 자체의 답(예: "주 150분")보다 개인 주의 사항이 앞섰습니다.

**Multi-Agent로 무엇이 좋아졌나**
- Supervisor가 경로를 고르고(100개 중 97개 정확, 건강 질문 외 40개는 40개 모두 정확), 본인·일반 질문을 구분합니다(60개 중 60개 정확). 일반 질문 점수 85.7% → 95.2%.
- 건강 질문 외 메시지 처리 35.0% → 97.5%, 평균 11.7초 → 2.3초, 메시지당 비용 약 1/14.
- 건강 질문은 약 2.7초 더 걸리고 비용도 약 27% 더 들지만(Supervisor 판단 1회, 식단+운동 질문의 두 Agent 검색), 100개 전체로는 Multi-Agent가 더 빠르고 저렴합니다.
- 본인 질문 점수는 90.9% ↔ 88.6%로 비슷합니다. 같은 Multi-Agent를 두 번 돌렸을 때도 92.7%와 88.6%로 달라졌으므로(4절), 약 4%포인트 안팎은 실력 차이로 보지 않습니다.

## 4. 한계와 Trade-off

### 4-1. Trade-off — 설계 선택으로 얻은 것과 잃은 것
| 설계 선택 | 얻은 것 | 잃은 것 (Trade-off) | 현재 보완 | 향후 개선 |
|---|---|---|---|---|
| 질문을 여러 검색어로 나누고 전문 Agent가 각각 처리 | 필수 답변을 뒷받침하는 논문 문장을 더 많이 찾았습니다(31.6% → 60.2%). 최종 답변 점수도 75.3%에서 91.5%로 높아졌습니다. | 검색어 생성과 근거 선택 단계가 추가되어 건강 질문의 평균 응답 시간이 4.1초에서 18.2초로 늘었습니다. 검색어 생성에 약 6초, 근거 선택에 약 3초가 걸렸습니다. | 처리 단계를 SSE로 실시간 표시합니다. 식단·운동 Agent는 동시에 실행하고, 논문 검색이 필요 없는 메시지는 바로 처리해 평균 2.3초로 줄였습니다. | 서로 독립적인 Query Transformation 단계를 병렬로 실행합니다. 4단계를 LLM 호출 한 번으로 합치는 방식은 대표 질문 6개 중 3개의 품질이 떨어져 채택하지 않습니다. |
| 논문 근거에서 확인된 내용만 답변에 사용 | 검색한 문단에 없는 내용을 답변에 섞는 일을 줄였습니다. 근거가 없는 질문 8개 중 7개에는 추측하지 않고 답변을 보류했습니다(PoC 결과). | 논문에 근거가 없지만 일반 지식으로는 답할 수 있는 내용도 “자료에 없다”고 답했습니다. 그 결과 Health Agentic RAG의 필수 답변 항목 중 10.3%가 0점을 받았습니다(Baseline 6.2%). | Supervisor가 일반 질문과 본인 질문을 구분하고 Safety Agent의 규칙을 함께 제공해, 최종 Multi-Agent의 0점 항목을 2.1%로 줄였습니다. | 논문에서 확인되지 않은 내용임을 먼저 밝힌 뒤, 일반 정보를 별도 구역으로 구분해 제공하는 형식을 검토합니다. |
| 완성된 답변을 code rule로 다시 검사 | 위험한 조언이나 꼭 필요한 저혈당 경고 누락을 사용자에게 전달하기 전에 막아, 최종 시스템의 안전 문제 답변을 0%로 낮췄습니다. | 문맥을 충분히 이해하지 못해 “하지 마세요” 같은 올바른 경고 문장까지 위험하다고 판단하는 오탐이 발생했습니다. 평가 중 올바른 문장 4개가 삭제됐습니다. | 오탐 원인 4가지를 수정하고 단위 테스트를 추가했습니다. 영향을 받은 답변 5개를 다시 실행한 결과 올바른 문장이 삭제된 사례는 0개였습니다. | code rule과 작은 classification model을 함께 사용해 문맥 판단을 보강합니다. |
| Supervisor가 메시지마다 담당 Agent를 선택 | 논문 검색이 필요 없는 기록·잡담·응급·서비스 요청을 별도 경로로 보내, 건강 질문 외 메시지 처리율을 35.0%에서 97.5%로 높였습니다. | 100개 중 3개에서 운동 질문을 식단·운동 혼합 질문으로 분류했습니다. 답변은 맞았지만 Diet Agent까지 실행되어 시간과 비용이 더 들었습니다. | 최종 답변 품질에는 문제가 없었고, routing 결과와 추가 실행 비용을 평가 로그에 기록했습니다. | 오분류된 질문을 Supervisor prompt의 예시와 routing 회귀 테스트에 추가합니다. |

## 6. 개발 비용

### 6-1. 운영 비용 추정 (GPT-6 Luna 가격 기준)
| 사용량 | 예상 비용 | 계산 근거 |
|---|---:|---|
| 건강 질문 1개 | 약 $0.0032 | 건강 질문 60개의 평균 |
| 건강 질문 외 메시지 1개 | 약 $0.00012 | 기록·잡담·응급·서비스 메시지 40개의 평균 |
| 평가와 같은 비율로 섞인 메시지 100개 | 약 $0.20 | 건강 질문 60개 + 그 외 메시지 40개 |

- 사용자 `n명`이 하루에 10개씩 질문할 때 예상 비용: **약 `$0.02 × n / 일`**
- 예) 사용자 1,000명 × 하루 10개 = 하루 10,000개 → **약 $20 / 일**
- 응급 메시지는 LLM을 부르지 않아 비용이 0입니다.

## 7. 느낀점

이번 프로젝트를 진행하면서 건강 상담 서비스는 답변을 잘 만드는 것만으로 충분하지 않다는 점을 배웠습니다. 사용자의 개인 건강정보를 질문과 함께 반영하되, 응급 상황·약 변경·기록 삭제처럼 일반적인 논문 검색만으로 처리할 수 없는 요청은 별도의 안전한 경로로 분리해야 했습니다.

또한 Multi-Agent는 Agent를 많이 추가하는 구조가 아니라, 요청에 필요한 역할만 나누고 각 결과를 안전하게 연결하는 설계라는 점을 확인했습니다. 품질과 안전성을 높인 대신 응답 시간과 비용이 증가했기 때문에, 앞으로는 현재 구조를 유지하면서 검색 단계 병렬화와 cache를 통해 더 빠르고 효율적인 서비스로 개선하고 싶습니다.
